# agentic-forecasting-tasks

ALE Tasks for live forecasting by general agents. Each forecasting target is one folder,
`tasks/live/<target>/`; contributing a target is a pull request that adds that folder and
nothing else. The pipeline that runs them, scores them and publishes the results is
[agentic-forecasting](https://github.com/rowingchenn/agentic-forecasting).

```text
tasks/
├── live/<target>/        written by the target's author; the same every day
└── mock/<target>/<d>/    generated by the pipeline after run day d; never edited by hand
```

All Tasks follow ALE's Task format, Harbor's `task.toml` (schema `1.4+ale.1`) and layout
([task-authoring.md](https://github.com/AgentsLastExam/ale/blob/main/docs/specs/task-authoring.md);
[ale-tasks-base](https://github.com/AgentsLastExam/ale-tasks-base) is the reference
collection). Git holds their text; their `environment/assets/`, `tests/assets/` and
`solution/assets/` folders are gitignored and live in the Hugging Face dataset
`<ALE_ASSETS_NAMESPACE>/agentic-forecasting-tasks`, synced with `ale assets push` and
`ale assets pull`.

## The live Task

An agent in the live Task receives the instruction, the day's schedule and the open
internet, and no data. It forecasts from whatever it finds, and saves the external
materials it used.

| File | Content |
|---|---|
| `task.toml` | the Task (public network, no sudo, 90 minutes, 8 CPUs and 32 GB of memory, the same for every target), the day's schedule and the target, see below |
| `instruction.md` | what to forecast, with the settlement definition precise enough to reproduce independently; the output format. ALE gives it to the agent verbatim |
| `environment/Dockerfile` | the sandbox: an ALE base image plus the libraries an agent is likely to want |
| `environment/setup/setup.sh` | writes `/home/user/input/task.json` (run date, target dates, cutoff, quantile levels) from the clock and the `AF_*` variables; in a continuing episode it first moves the previous day's output to `/home/user/history/<run date>/` |
| `tests/` | `test.sh` and `verify.py` check that the submission is well-formed (accuracy is scored after the real values are published); `fetch.py` is where the target's numbers come from, run by the pipeline on the host. ALE uploads `tests/` only to verify, after the agent has finished, so no agent sees `fetch.py` |
| `solution/solve.sh` | a well-formed submission for `ale validate` |

`task.toml` defines the target as the tuple (y, Δ, H, X, B) of the research draft. ALE
rejects unknown keys, so the schedule lives in `[environment.env]`, which setup reads, and
the target in `[metadata.agentic-forecasting]`, which ALE leaves alone. Keep the metadata
tables last in the file.

| Field | Meaning |
|---|---|
| `[environment.env]` `AF_TIMEZONE`, `AF_CUTOFF` | submissions are due at the cutoff, local time on the run date |
| `AF_HORIZONS` | target dates as days after the run date, a JSON list |
| `AF_QUANTILE_LEVELS` | the quantiles every forecast submits, a JSON list |
| `[metadata].network_justification` | why the Task needs the public internet (`ale lint` requires it) |
| `…agentic-forecasting` `title`, `question`, `summary`, `region`, `unit` | shown on the website; `question` is the one-sentence statement of what is forecast |
| `…taxonomy`, `driver`, `tradable` | where the task sits in [`taxonomy.yaml`](taxonomy.yaml): a `<domain>/<leaf>`, the driver facet, and whether it is a tradable control |
| `…y` | the series, its source and how it is settled (first published value) |
| `…schedule.snapshot` | when a run day starts, in `AF_TIMEZONE` |
| `…schedule.every_days`, `first_run` | a run day every `every_days` days from `first_run`; truth is recorded daily regardless |
| `…x` | X_d: the curated input the TSFMs receive. Each column group has `what` it is and `why` it should help, in plain words, plus its source; the website shows them as written. `expert = true` marks the earlier official forecast, which only the `*-expert` TSFMs get |
| `…baseline` | B: `system` id, `label`, the official or expert forecast and how it is read; `visible_to_agents`, whether the agents can see that issue during the run; `reference = true` for a tradable control's no-change price. Leave the table out when no public expert forecast exists |

Write the schedule into `instruction.md` as well, in words; ALE no longer fills templates.
Two paragraphs of the instruction are shared by every target and must stay verbatim,
because the pipeline swaps them for a replay (`af/mock.py`): the one on internet access
("You have unrestricted internet access…") and the one on collected materials ("Save
copies of the external materials…"). Copy them from an existing target. Do not write about
earlier run days: for an agent that continues from its previous run day, the pipeline adds
that paragraph after the one on internet access (`af continual-task`).

### Choosing the schedule

The website's [Methods](https://chennzi-agentic-forecasting.static.hf.space/#/methods?at=definition)
page states the tuple and its timing rules formally. For an author they come down to these
steps, in this order:

1. **y.** A daily or weekly series that an authority publishes continuously, settled on
   its first published value; a weekly target date is the date that labels the week.
   Define it in `instruction.md` precisely enough for someone else to recompute it: the
   report, the aggregation, the local day, and how many observations a day needs to count.
2. **B.** The public expert or official forecast of the same y, and the issue of it you
   compare with. Find when it has come out over at least a year of history.
3. **Start (`schedule.snapshot`).** After the latest target value is published; this is
   the one hard rule. X_d is taken at the start too, so the agents and the TSFMs begin
   from the same latest value.
4. **Cutoff (`AF_CUTOFF`).** At least 1 h 45 min after the start, for the agents' 90
   minutes plus building and setting up the sandbox, and before any observation of the
   first target date. Where the schedule allows, put it a few minutes before B's issue and
   compare with that first issue after the cutoff: the agents then forecast from nearly
   the information B uses and never see it. The NWS evening forecast for St. Louis came
   out at 18:45 at the earliest over 400 days, so the cutoff is 18:40; ECCC issues its
   Toronto forecast at 06:00, so the cutoff is 05:50; ERCOT posts a new version every hour,
   and the cutoff 09:25 makes the 09:30 version the comparison. Where B comes out soon
   after the latest value, or in the same release, start after the value anyway and
   compare with the issue the agents can see (National Gas's 13:01 forecast, Norges Bank's
   Monday release). Either way, set `visible_to_agents` in the baseline table.
5. **Horizons (`AF_HORIZONS`).** The dates B forecasts, counted from the run date: 1–7 for
   ERCOT's seven-day forecast, 1–13 for the NWS forecast, 0 and 1 for ECCC's Today and
   Tomorrow. Use 0 only when the run day's target period starts after the cutoff
   (Toronto's daytime maximum covers 07:00 to 18:00).
6. **Quantiles (`AF_QUANTILE_LEVELS`).** 0.1 to 0.9, as every target uses, so that scores
   compare across tasks.
7. **Run days (`schedule.every_days`).** Daily or weekly; the maintainer sets `first_run`
   when enabling the timer.
8. **X.** The target history and the covariates you would give a forecaster, each as
   published before the start. Include the previous cycle's issue of B (the one before
   B's own) as a group with `expert = true`, never B's own issue, so that the `-expert`
   TSFMs get the same kind of help on every target.

Without an expert forecast, leave out the baseline table; steps 3 and 4 reduce to two
conditions: start after the latest value is published, and cut off before any observation
of the first target date.

### fetch.py

`tests/fetch.py` uses only the standard library and pandas, and reads credentials from
environment variables that the pipeline loads from its `.env`. It defines three functions;
`spec` is `[metadata.agentic-forecasting]` with the `AF_*` schedule merged in (`horizons`,
`quantiles`, `schedule.timezone`, `schedule.cutoff`).

- `snapshot(run_date, spec)` returns X_d as published at call time, a dict with:
  - `series`: a daily `DataFrame` indexed by date from `x.history_start` to the last
    target date, with a `target` column empty after the last complete day and covariate
    columns known through the forecast window;
  - `last_observed`: the last date with a target value;
  - `raw`: `{file name: DataFrame}` of the finer-grained data `series` was derived from;
  - `sources`: where each part came from; `covariate_notes`: what each column means.
- `truth(today, spec)` returns a date-indexed `Series` of every value published so far.
- `baseline(run_date, spec)` returns `{"source": {...}, "forecasts": [{"target_date":
  ..., "point": ...}]}` (or `"quantiles"` instead of `"point"`) for the issue the Task
  compares with (step 4). The pipeline calls it every day for the run days of the past
  week that lack it, so the issue must still be retrievable a few days later; before it
  is published, `forecasts` is empty.

Earlier versions of the official forecast stay public. Where the publisher keeps them,
give the TSFMs the previous cycle's issue as a covariate (step 8). Published history that never changes may be
cached on the host under `~/.cache/agentic-forecasting/<target>/`, as ERCOT's past forecast
versions are.

The pipeline writes the files (`series.csv`, `raw/`, `task.json`, `MANIFEST.json` with
SHA-256 hashes) and refuses to build X_d for any day but today, so no value published
later can enter it.

## Mock Tasks

After run day d, the pipeline turns the live Task into `tasks/mock/<target>/<d>/`, the
offline replay of that day (`af/mock.py` in the pipeline repository):

- no network (`network_mode = "no-network"`), and hosted web search disabled through the
  agents' managed settings, since it runs at the model provider outside the sandbox network;
- `environment/assets/task.json`: the schedule the live agents saw;
- `environment/assets/archive/<system>/`: the files each live agent saved with a web
  source, with their `index.jsonl`. The image installs both read-only under
  `/home/user/input/`; a replay has no setup stage;
- `solution/assets/x/`: X_d. ALE uploads `solution/` only for oracle episodes, so the
  reference solution (a weekly seasonal naive forecast) uses it and no agent sees it.

The replays do not run on their own: the pipeline builds one per run day, and an agent
replays it only when someone starts it.

Every mock Task is a self-contained offline benchmark item:

```bash
ale assets pull tasks/mock/ercot_peak_load/2026-10-22
ale validate tasks/mock/ercot_peak_load/2026-10-22
ale run tasks/mock/ercot_peak_load/2026-10-22 --config <agent>.toml
```

## Taxonomy

[`taxonomy.yaml`](taxonomy.yaml) organises targets by the system that generates the series
(energy, public health, economy and labor, financial markets, environment, space,
transport and mobility, online attention), with leaves inside each domain and two facets across them:
the main driver of variation, and whether the target is a tradable price (a control).
Every live Task names one leaf. The website counts tasks per node, empty ones included,
and lists candidate targets for the gaps, so new targets can be chosen for coverage.
Revise the taxonomy in the same pull request when a target fits no leaf.

## Adding a target

1. Copy `tasks/live/ercot_peak_load` to `tasks/live/<target>`. Keep the Task name
   `agentic-forecasting/<target with dashes>-live`.
2. Rewrite `task.toml` (the `AF_*` schedule, `question`, `taxonomy` and the `what`/`why`
   of each covariate group), `instruction.md` and `tests/fetch.py`; add libraries to
   `environment/Dockerfile` if the target needs them. `environment/setup/`, the verifier
   and `solution/` work for any target.
3. Check it from the pipeline repository, next to this one:

   ```bash
   uv run python -m af snapshot <target>         # X_d of today, into tasks/mock/<target>/<today>/
   uv run python -m af truth <target>
   uv run python -m af baseline <target> <today>
   scripts/ale validate ../agentic-forecasting-tasks/tasks/live/<target>
   ```

4. Open a pull request with `tasks/live/<target>/` only. The maintainer adds the
   credentials of its data sources to the pipeline's `.env` and enables its timer.

`just lint` checks every Task with the engine of the sibling pipeline repository.
